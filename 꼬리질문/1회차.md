### MVVM 패턴의 각 컴포넌트들은 어떤 역할을 수행하나요?
- **용어 설명**
  - **MVVM(Model-View-ViewModel)**: UI와 비즈니스 로직을 분리해 유지보수성과 테스트 용이성을 높이는 아키텍처 패턴.

- **세부 설명**
  - **Model**: 앱의 데이터와 비즈니스 로직을 담당. Repository, UseCase 등 데이터 처리 계층이 포함됨.
  - **View**: UI와 사용자 입력 처리 담당. 데이터 표시와 이벤트 전달 역할.
  - **ViewModel**: View와 Model 사이의 중간자 역할. UI 상태 관리와 비즈니스 로직 호출, LiveData/StateFlow로 View에 데이터 전달.
  - 예시 코드:
    ```kotlin
    class MainViewModel(private val repo: UserRepository) : ViewModel() {
        val userData = MutableLiveData<User>()
        fun loadUser() {
            userData.value = repo.getUser()
        }
    }
    ```

- **장점**
  - **관심사 분리**: UI, 로직, 데이터 계층이 분리돼 유지보수 쉬움.
  - **테스트 용이성**: View를 제외한 비즈니스 로직을 독립적으로 테스트 가능.
  - **재사용성**: ViewModel은 여러 View에서 재사용 가능.

- **단점/주의점**
  - **구현 복잡성 증가**: 간단한 앱에도 구조가 커질 수 있음.
  - **학습 곡선**: 초보자에겐 개념 이해와 적용이 어렵다.

- **핵심 답변 요약**
  - UI, 데이터, 로직을 각각 View, Model, ViewModel로 분리해 유지보수와 테스트를 쉽게 함.

- **면접 대답용**
  > "MVVM은 UI(View)와 비즈니스 로직(Model)을 ViewModel로 연결해 관심사를 분리하는 구조입니다."

---

### MVVM 패턴에서 ViewModel과 View 간의 양방향 데이터 바인딩은 어떻게 이루어지나요?
- **용어 설명**
  - **양방향 데이터 바인딩**: View와 ViewModel 간 데이터 변경이 서로 자동 반영되는 방식.

- **세부 설명**
  - View → ViewModel: EditText 같은 입력 UI에서 값이 변경되면 BindingAdapter나 ObservableField가 ViewModel의 필드에 반영.
  - ViewModel → View: ViewModel 필드 변경 시 Observer나 Data Binding이 UI에 자동 반영.
  - 예시 코드:
    ```xml
    <EditText
        android:text="@={viewModel.userName}" />
    ```

- **장점**
  - **코드 간소화**: UI 갱신 및 이벤트 처리 코드 감소.
  - **실시간 동기화**: 양쪽 데이터가 항상 일치.

- **단점/주의점**
  - **디버깅 어려움**: 데이터 흐름 추적이 복잡.
  - **성능 문제 가능성**: 불필요한 바인딩 이벤트 발생.

- **핵심 답변 요약**
  - View와 ViewModel의 필드를 연결해 한쪽 변경이 다른 쪽에 즉시 반영되도록 함.

- **면접 대답용**
  > "양방향 데이터 바인딩은 View와 ViewModel을 연결해 변경 사항이 양쪽에 자동 반영되게 합니다."

---

### MVVM의 데이터 바인딩은 어떤 이점을 가지고 있는지 설명해주세요.
- **용어 설명**
  - **데이터 바인딩**: UI 컴포넌트를 데이터 소스와 연결해 코드 없이 자동으로 동기화하는 기법.

- **세부 설명**
  - XML 레이아웃에서 ViewModel 데이터에 직접 접근 가능.
  - findViewById 호출 없이 UI 갱신.
  - 예시 코드:
    ```xml
    <TextView
        android:text="@{viewModel.userName}" />
    ```

- **장점**
  - **코드 간결화**: View 참조와 setText 등 수동 UI 갱신 제거.
  - **유지보수성 향상**: UI 변경이 ViewModel 변경 없이 가능.

- **단점/주의점**
  - **런타임 에러 위험**: XML 바인딩 구문 오류 시 빌드 에러 대신 런타임에서 문제 발생 가능.
  - **학습 곡선**: 바인딩 표현식과 라이프사이클 개념 필요.

- **핵심 답변 요약**
  - UI와 데이터의 동기화를 단순화해 코드 양과 유지보수 비용을 줄임.

- **면접 대답용**
  > "데이터 바인딩은 UI와 데이터를 직접 연결해 코드량을 줄이고 유지보수성을 높입니다."

### MVVM 패턴을 사용할 때 주의해야 할 점은 무엇인가요?
- **세부 설명**
  - ViewModel이 비대해지지 않도록 역할 분리 필요.
  - LiveData나 Observable 객체는 메모리 누수 없이 관리.
  - 데이터 바인딩 과도 사용 시 성능 저하 가능.

- **장점**
  - (없음 — 주의사항 질문이므로)

- **단점/주의점**
  - **ViewModel 비대화**: 모든 로직이 ViewModel에 몰리면 관리 어려움.
  - **메모리 누수 위험**: Observer 해제 누락 시 발생.

- **핵심 답변 요약**
  - ViewModel과 다른 계층의 책임을 명확히 구분하고 바인딩 관리에 신경 써야 함.

- **면접 대답용**
  > "MVVM은 책임 분리를 유지하고 메모리 누수를 방지하는 것이 중요합니다."

---

### MVVM 패턴에서 ViewModel이 너무 커지면 어떤 문제가 발생할 수 있나요?
- **세부 설명**
  - **God ViewModel** 현상: 모든 로직이 집중돼 단일 책임 원칙 위반.
  - 테스트 어려움, 유지보수 난이도 증가.

- **장점**
  - (없음)

- **단점/주의점**
  - **변경 영향 범위 확대**: 작은 변경도 여러 기능에 영향.
  - **가독성 저하**: 코드 구조 파악 어려움.

- **핵심 답변 요약**
  - ViewModel 비대화는 유지보수성과 테스트성을 저하시킴.

- **면접 대답용**
  > "ViewModel이 커지면 단일 책임 원칙이 깨져 유지보수가 어렵습니다."

---

### MVVM 패턴에서 데이터 바인딩이 어떻게 동작하는지 설명해주세요.
- **세부 설명**
  - 컴파일 시 Binding 클래스 생성.
  - XML 표현식 → ViewModel 데이터 → UI 요소에 매핑.
  - LiveData 변경 시 Observer를 통해 UI 자동 업데이트.

- **장점**
  - **자동 UI 갱신**: 데이터 변경 시 별도 코드 필요 없음.
  - **타입 안정성**: 컴파일 시점에 타입 체크 가능.

- **단점/주의점**
  - **성능 부담**: 바인딩 표현식 과도 사용 시 성능 저하.

- **핵심 답변 요약**
  - 컴파일러가 생성한 Binding 클래스로 View와 데이터가 연결돼 자동 동기화됨.

- **면접 대답용**
  > "데이터 바인딩은 컴파일 시 Binding 클래스를 생성해 View와 데이터를 자동 연결합니다."

### MVVM에서의 One-way binding과 Two-way binding의 차이점은 무엇인가요?
- **용어 설명**
  - **One-way binding**: 데이터 → UI 단방향 반영.
  - **Two-way binding**: 데이터 ↔ UI 양방향 반영.

- **세부 설명**
  - One-way: UI 표시 전용 데이터.
  - Two-way: 입력 UI와 데이터 모델이 상호 업데이트.

- **장점**
  - **One-way**: 단순하고 성능 부담 적음.
  - **Two-way**: 입력값과 상태 동기화 편리.

- **단점/주의점**
  - **One-way**: UI 입력 반영 시 추가 코드 필요.
  - **Two-way**: 디버깅 복잡, 불필요 이벤트 발생 가능.

- **핵심 답변 요약**
  - One-way는 읽기 전용, Two-way는 읽기/쓰기를 모두 자동 반영.

- **면접 대답용**
  > "One-way는 데이터만 UI로, Two-way는 양쪽 변경이 즉시 반영됩니다."

---

### View와 ViewModel의 데이터 동기화 및 바인딩은 어떻게 이루어지나요?
- **세부 설명**
  - LiveData/StateFlow와 Observer 패턴 사용.
  - ViewModel에서 값 변경 → Observer가 감지 → UI 업데이트.
  - UI 이벤트는 ViewModel 메서드 호출로 데이터 변경.

- **장점**
  - **명확한 흐름**: 단방향 데이터 흐름 유지 가능.
  - **유지보수성**: 데이터 변경 지점이 명확.

- **단점/주의점**
  - **중복 Observer 등록 위험**: 메모리 누수 가능.

- **핵심 답변 요약**
  - ViewModel 데이터는 Observer로 View에 전달되고, UI 입력은 ViewModel 메서드로 반영.

- **면접 대답용**
  > "LiveData나 StateFlow로 ViewModel과 View를 연결해 데이터 동기화를 유지합니다."

### LiveData와 ObservableField의 차이는 무엇이고, 왜 LiveData를 ViewModel에서 더 권장하는 이유는 무엇인가요?
- **용어 설명**
  - **LiveData**: 생명주기 인식 가능 데이터 홀더 클래스.
  - **ObservableField**: Data Binding 전용 관찰 가능 필드.

- **세부 설명**
  - LiveData는 생명주기를 인식해 UI 업데이트 시점 관리.
  - ObservableField는 간단하지만 생명주기 관리 없음.

- **장점**
  - **LiveData**: 메모리 누수 방지, 라이프사이클 안전.
  - **ObservableField**: 구현 단순, 데이터 바인딩 용이.

- **단점/주의점**
  - **LiveData**: XML 바인딩 문법이 다소 길다.
  - **ObservableField**: 수명 관리 안 되어 비효율 가능.

- **핵심 답변 요약**
  - LiveData는 라이프사이클 안전성이 높아 권장됨.

- **면접 대답용**
  > "LiveData는 라이프사이클을 인식해 안전하게 UI를 갱신할 수 있어 권장됩니다."

### LiveData의 장점 중 하나인 라이프사이클 인식은 어떤 상황에서 유용하게 활용될 수 있는가요?
- **세부 설명**
  - Activity/Fragment가 비활성 상태일 때 불필요한 UI 업데이트 방지.
  - 예: 화면 전환 중 네트워크 응답 도착 시 UI 갱신 생략.

- **장점**
  - **리소스 절약**: 불필요한 연산 방지.
  - **안정성 향상**: 잘못된 UI 상태 업데이트 방지.

- **단점/주의점**
  - **백그라운드 작업 중단**: 필요 시 별도 관리 필요.

- **핵심 답변 요약**
  - 라이프사이클 인식으로 UI 안전성과 효율성을 동시에 확보.

- **면접 대답용**
  > "라이프사이클 인식은 비활성 UI에 불필요한 업데이트를 방지합니다."

### Android Architecture Components에서는 이러한 문제를 해결하기 위해 어떤 구성 요소를 제공하고 있나요?
- **세부 설명**
  - ViewModel, LiveData, Room, Data Binding, Navigation 등 제공.
  - 라이프사이클 관리, 데이터 저장, UI 바인딩을 쉽게 구현 가능.

- **장점**
  - **생명주기 안전성**: 메모리 누수 최소화.
  - **구현 단순화**: 표준화된 컴포넌트 제공.

- **단점/주의점**
  - **버전 호환성**: 일부 최신 기능은 구 버전에서 제한.

- **핵심 답변 요약**
  - AAC는 표준 컴포넌트로 생명주기·데이터·UI 처리를 단순화.

- **면접 대답용**
  > "AAC는 ViewModel, LiveData, Room 등으로 표준화된 아키텍처 구현을 돕습니다."

### Android에서 ViewModel과 View를 연결하는 방법은 무엇이 있고, 각각의 장단점은 무엇인가요?
- **용어 설명**
  - **LiveData/Flow**: 관찰 가능한 데이터 홀더(라이프사이클 인식/스트림).
  - **Data Binding**: XML에서 데이터 표현식을 통해 View와 데이터를 연결.
  - **Jetpack Compose State**: 선언적 UI에서 `State` 중심으로 UI를 재구성.

- **세부 설명**
  - 상황 설명  
    - ViewModel이 제공하는 상태를 View에서 관찰/수집하여 UI를 갱신한다. 구현 방식에 따라 옵저버 패턴, 바인딩, 선언적 상태 수집으로 나뉜다.
  - 구체적인 동작/원리  
    - LiveData: `observe(LifecycleOwner)`로 활성 상태에서만 콜백.  
    - Flow: `collect`/`collectLatest`, Android에선 `repeatOnLifecycle`과 함께 사용.  
    - Data Binding: 컴파일 시 생성된 바인딩 클래스로 XML ↔ ViewModel 속성 연결.  
    - Compose: `collectAsStateWithLifecycle()` 등으로 상태를 수집하여 리컴포지션.
  - 예시 코드나 상황 예시
    ```kotlin
    // LiveData
    viewModel.state.observe(viewLifecycleOwner) { render(it) }

    // Flow in Fragment
    viewLifecycleOwner.lifecycleScope.launch {
      viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.state.collect { render(it) }
      }
    }

    // Data Binding (XML)
    <TextView android:text="@{viewModel.title}" />

    // Compose
    val state by viewModel.state.collectAsStateWithLifecycle()
    ```

- **장점**
  - LiveData/Flow는 라이프사이클 인식이 좋다 (비활성 UI에 업데이트를 막아 누수/크래시를 예방).
  - Data Binding은 보일러플레이트 제거가 좋다 (`findViewById`, `setText` 등의 반복 코드 감소).
  - Compose State는 선언적 패러다임이 좋다 (상태 변화에 따른 자동 리컴포지션으로 UI 일관성 확보).

- **단점/주의점**
  - LiveData는 이벤트 처리에 안 좋다 (단발성 이벤트 중복소비 이슈 → `SharedFlow`/`Channel` 권장).
  - Data Binding은 디버깅/빌드 속도에 안 좋다 (표현식 복잡도↑, 빌드 느려질 수 있음).
  - Compose는 러닝 커브/상태 설계 미숙 시 안 좋다 (리컴포지션/스냅샷 이해 부족 시 버그 유발).

- **핵심 답변 요약**
  - 상황: ViewModel 상태를 View에 반영해야 한다  
  - 원인: MVVM에서 UI-로직 분리로 관찰/수집 메커니즘 필요  
  - 해결 방법: LiveData/Flow(옵저버), Data Binding(XML), Compose(State) 중 요구사항에 맞게 선택

- **면접 대답용**
  > “안드로이드는 LiveData/Flow 옵저버, Data Binding, 그리고 Compose의 State 수집으로 VM↔View를 연결합니다. 저는 라이프사이클 안전성과 유지보수를 고려해 상황별로 선택합니다.”

### MVVM 아키텍처에서도 View가 ViewModel을 생성하는 것이 아니라, Dependency Injection을 통해 외부에서 ViewModel을 주입하는 방법이 있습니다. 이 방법의 장단점은 무엇인가요?
- **용어 설명**
  - **DI(Dependency Injection)**: 객체 생성/연결을 외부 컨테이너가 담당하는 패턴(Hilt/Dagger/Koin 등).

- **세부 설명**
  - 상황 설명  
    - View에서 직접 ViewModel을 만들면 생성자 의존성/스코프/테스트 대체가 어려워진다.
  - 구체적인 동작/원리  
    - `@HiltViewModel` + `@AndroidEntryPoint`로 ViewModel을 주입받고, 의존성은 모듈에서 바인딩한다.
  - 예시 코드나 상황 예시
    ```kotlin
    @HiltViewModel
    class MainViewModel @Inject constructor(
      private val repo: UserRepository
    ) : ViewModel()

    @AndroidEntryPoint
    class MainFragment: Fragment(R.layout.main) {
      private val vm: MainViewModel by viewModels()
    }
    ```

- **장점**
  - 결합도 감소가 좋다 (View는 생성 책임에서 벗어나고 테스트 더블 주입이 쉬워짐).
  - 재사용성과 일관성이 좋다 (생성 정책/스코프를 중앙에서 관리).

- **단점/주의점**
  - 설정 복잡성이 안 좋다 (DI 러닝 커브와 그래프 관리 비용).
  - 스코프 불일치 위험이 안 좋다 (잘못 주입 시 메모리 누수/상태 공유 문제).

- **핵심 답변 요약**
  - 상황: View가 ViewModel을 직접 만들면 확장성과 테스트성이 떨어짐  
  - 원인: 생성 책임/스코프/의존 관리가 분산  
  - 해결 방법: DI로 ViewModel과 의존성을 주입하고 스코프를 표준화

- **면접 대답용**
  > “ViewModel은 DI로 주입해 생성/스코프/테스트를 통제합니다. 덕분에 결합도는 낮아지고 테스트는 쉬워집니다.”


---

### DI를 통해 ViewModel을 주입받을 때 주의할 점은 무엇이 있고, 이를 해결하기 위한 방법은 무엇인가요?
- **용어 설명**
  - **ViewModel 스코프**: `@ViewModelScoped`, `@ActivityRetainedScoped`, `@Singleton` 등 DI 수명 범위.

- **세부 설명**
  - 상황 설명  
    - 잘못된 스코프 설정/런타임 인자 주입/Context 참조/스레딩 고정 등으로 결함이 발생할 수 있다.
  - 구체적인 동작/원리  
    - 스코프 일치: Owner 범위에 맞춘 의존성 주입.  
    - 런타임 인자: `SavedStateHandle`/`@Assisted`로 처리.  
    - 스레딩: `CoroutineDispatcher`를 DI로 주입해 테스트 대체 용이.
  - 예시 코드나 상황 예시
    ```kotlin
    @HiltViewModel
    class DetailVM @Inject constructor(
      private val repo: Repo,
      @IoDispatcher private val io: CoroutineDispatcher,
      private val state: SavedStateHandle
    ) : ViewModel() {
      val id: String = state["id"] ?: error("id missing")
    }
    ```

- **장점**
  - 테스트 용이성이 좋다 (디스패처/Repo를 테스트 대체 가능).
  - 안정성이 좋다 (스코프/런타임 인자 표준화로 누수/오동작 감소).

- **단점/주의점**
  - DI 구성 실수는 안 좋다 (런타임 주입 오류/순환 의존).
  - 초기화 오버헤드는 안 좋다 (과도한 모듈/그래프는 빌드/런타임 비용 증가).

- **핵심 답변 요약**
  - 상황: DI 기반 ViewModel 주입 시 다양한 결함 가능  
  - 원인: 스코프 불일치, 런타임 인자/Context/스레딩 처리 미숙  
  - 해결 방법: 올바른 스코프, `SavedStateHandle`/Assisted, `@ApplicationContext`, 디스패처 주입

- **면접 대답용**
  > “스코프는 Owner에 맞추고, 런타임 인자는 `SavedStateHandle`, Context는 앱 컨텍스트만, 디스패처는 DI로 주입해 테스트 가능하게 설계합니다.”


---

### Fragment의 생명주기와 ViewModel의 생명주기가 서로 어떻게 관련되어 있는지 설명해주세요.
- **용어 설명**
  - **ViewModelStoreOwner**: ViewModel 생존을 관리하는 Owner(Fragment/Activity/NavBackStackEntry).
  - **View Lifecycle**: `onCreateView`~`onDestroyView` 사이의 뷰 수명(뷰는 사라져도 Fragment/VM은 남을 수 있음).

- **세부 설명**
  - 상황 설명  
    - Fragment는 뷰 수명과 인스턴스 수명이 다르며, ViewModel은 Owner가 파괴될 때까지 유지된다.
  - 구체적인 동작/원리  
    - `by viewModels()`(Fragment 스코프), `by activityViewModels()`(Activity 공유), `navGraphViewModels()`(그래프 스코프).
  - 예시 코드나 상황 예시
    ```kotlin
    // 그래프 공유 VM
    val vm: MyVM by navGraphViewModels(R.id.flow_graph)
    ```

- **장점**
  - 상태 공유가 좋다 (필요한 범위에서만 동일 VM 공유로 중복 호출 방지).
  - 구성 변경 내구성이 좋다 (Owner 유지 시 VM 재사용).

- **단점/주의점**
  - View 참조 보관은 안 좋다 (뷰가 파괴돼도 VM이 살아 누수 위험).
  - 스코프 오용은 안 좋다 (불필요한 범위 공유로 메모리/상태 오염).

- **핵심 답변 요약**
  - 상황: Fragment/뷰/VM의 수명이 다름  
  - 원인: VM은 Owner 기준, 뷰는 View Lifecycle 기준  
  - 해결 방법: 올바른 스코프 선택, VM에 View/Context 직접 참조 금지

- **면접 대답용**
  > “VM은 Fragment/Activity/네비그래프 스코프에 묶여 살고, 뷰 수명과는 별개라 View 참조를 VM에 두지 않습니다.”

### Fragment의 재생성 및 구성 변경 시 ViewModel이 유지되는 방법에 대해 더 자세히 설명해주실 수 있나요?
- **용어 설명**
  - **Non-Config 인스턴스**: 구성 변경 시에도 유지되는 객체(내부적으로 VMStore가 보존).

- **세부 설명**
  - 상황 설명  
    - 회전/다크모드 등으로 Fragment가 재생성되어도 같은 Owner 범위의 ViewModel은 유지된다.
  - 구체적인 동작/원리  
    - `ViewModelProvider`가 `ViewModelStore`에서 기존 인스턴스를 찾아 반환.  
    - 프로세스 죽음은 예외 → `SavedStateHandle`/DB로 복원.
  - 예시 코드나 상황 예시
    ```kotlin
    class MyVM: ViewModel()
    class MyFragment: Fragment(R.layout.f) {
      private val vm: MyVM by viewModels() // 회전 후에도 동일
    }
    ```

- **장점**
  - 재요청 방지가 좋다 (네트워크/연산 중복 감소).
  - UX가 좋다 (상태 지속으로 깜빡임/리로딩 최소화).

- **단점/주의점**
  - 프로세스 죽음엔 안 좋다 (VM이 소멸 → 상태 저장 필요).
  - 대용량 보관은 안 좋다 (메모리 사용↑, 누수 위험).

- **핵심 답변 요약**
  - 상황: 구성 변경으로 Fragment 재생성  
  - 원인: VMStore 보존으로 동일 VM 재사용  
  - 해결 방법: 동일 스코프로 VM 획득, 프로세스 죽음 대비 `SavedStateHandle`/영속 저장

- **면접 대답용**
  > “재생성돼도 같은 Owner면 `ViewModelStore`가 살아 있어 기존 ViewModel을 재사용합니다.”


---

### ViewModel의 생명주기를 설명하고, 화면 회전 시 ViewModel이 어떤 변화를 겪는지 설명하세요.
- **용어 설명**
  - **onCleared()**: Owner가 소멸될 때 자원 해제 콜백.

- **세부 설명**
  - 상황 설명  
    - ViewModel은 Owner(Activity/Fragment/NavBackStackEntry)가 파괴될 때까지 유지된다.
  - 구체적인 동작/원리  
    - 회전 같은 구성 변경에서는 Owner가 교체되지만 같은 스코프의 VMStore가 유지되어 VM도 유지, `onCleared()` 미호출.
  - 예시 코드나 상황 예시
    ```kotlin
    class VM: ViewModel() {
      override fun onCleared() { /* cancel jobs */ }
    }
    ```

- **장점**
  - 상태 유지가 좋다 (회전에도 데이터 보존).
  - 비용 절감이 좋다 (재계산/재호출 최소화).

- **단점/주의점**
  - 종료 시점 혼동은 안 좋다 (UI 소멸=VM 소멸 아님).
  - View/Context 보관은 안 좋다 (누수 위험).

- **핵심 답변 요약**
  - 상황: 회전 발생  
  - 원인: VMStore 보존으로 VM 유지  
  - 해결 방법: 자원 해제는 `onCleared()`에서, VM에 UI 참조 금지

- **면접 대답용**
  > “회전 시엔 VM이 유지되고, Owner가 완전히 끝날 때만 `onCleared()`가 호출됩니다.”

### ViewModel의 onSaveInstanceState()와 onRestoreInstanceState() 메서드의 차이점은 무엇인가요?
- **용어 설명**
  - **onSaveInstanceState/ onRestoreInstanceState**: `Activity`/일부 `Fragment`의 상태 저장/복원 콜백(※ ViewModel에는 없음).

- **세부 설명**
  - 상황 설명  
    - VM에는 해당 콜백이 없고, **상태 보존은 UI 컨트롤러**에서 수행하며 VM은 `SavedStateHandle`로 협력한다.
  - 구체적인 동작/원리  
    - 저장: `Activity.onSaveInstanceState(outState)`에서 번들에 최소 상태 기록.  
    - 복원: `onCreate(savedInstanceState)`/`onRestoreInstanceState()`에서 읽어 UI/VM 초기화.  
    - VM: 생성자 주입된 `SavedStateHandle`을 통해 동일 키로 접근.
  - 예시 코드나 상황 예시
    ```kotlin
    // Activity
    override fun onSaveInstanceState(out: Bundle) {
      out.putString("q", binding.et.text.toString())
      super.onSaveInstanceState(out)
    }

    // ViewModel
    @HiltViewModel
    class VM @Inject constructor(private val state: SavedStateHandle): ViewModel() {
      var q: String
        get() = state["q"] ?: ""
        set(v) { state["q"] = v }
    }
    ```

- **장점**
  - 역할 분리가 좋다 (UI 콜백은 컨트롤러, 지속 상태는 VM 협업).
  - 프로세스 죽음 복원이 좋다 (핵심 입력 복원 가능).

- **단점/주의점**
  - 대용량 저장은 안 좋다 (바인더 트랜잭션 제한/성능 저하).
  - 키 충돌/스키마 변경은 안 좋다 (버전 호환 전략 필요).

- **핵심 답변 요약**
  - 상황: 상태 저장/복원이 필요  
  - 원인: VM엔 onSave/Restore 없음, UI 콜백+`SavedStateHandle`로 협업  
  - 해결 방법: 최소 상태만 번들에, 나머지는 VM/영속 저장 활용

- **면접 대답용**
  > “onSave/Restore는 ViewModel이 아닌 UI 콜백이고, VM은 `SavedStateHandle`로 상태를 이어갑니다.”

### 번들(Bundle) 객체가 onSaveInstanceState()와 onRestoreInstanceState()에서 어떻게 활용되는지 자세히 설명해주세요.
- **용어 설명**
  - **Bundle**: 직렬화 가능한 Key-Value 컨테이너.

- **세부 설명**
  - 상황 설명  
    - 구성 변경/프로세스 사망 대비로 “최소 UI 상태”를 보존한다.
  - 구체적인 동작/원리  
    - 저장: `onSaveInstanceState`에서 `putXxx(key, value)`로 기록.  
    - 복원: `onCreate(saved)`/`onRestoreInstanceState(saved)`/`Fragment.onViewStateRestored(saved)`에서 읽어 UI 초기화.
  - 예시 코드나 상황 예시
    ```kotlin
    override fun onSaveInstanceState(out: Bundle) {
      out.putParcelable("user", userParcelable)
      out.putStringArrayList("ids", arrayListOf("a","b"))
      super.onSaveInstanceState(out)
    }
    ```

- **장점**
  - 빠른 복원이 좋다 (프로세스 사망 후도 즉시 상태 재구성).
  - 플랫폼 지원이 좋다 (시스템이 자동으로 전달/복원 트리거).

- **단점/주의점**
  - 용량 제한이 안 좋다 (~1MB 수준 트랜잭션 제한/장치별 차이).
  - 타입 제약이 안 좋다 (직렬화 가능/경량 데이터만 권장).

- **핵심 답변 요약**
  - 상황: 일시적 UI 상태 보존 필요  
  - 원인: 구성 변경/프로세스 사망  
  - 해결 방법: Bundle에 경량 상태 저장, 복원 콜백에서 UI 재설정

- **면접 대답용**
  > “번들은 콜백 사이에서 최소 상태를 보존하는 컨테이너라, 저장은 `onSave…`, 복원은 `onCreate/…Restored`에서 합니다.”

### Android에서 Bundle 객체에 어떤 종류의 데이터를 저장할 수 있고, 복원할 수 있는지 자세히 설명해주세요.
- **용어 설명**
  - **Parcelable/Serializable**: 객체 직렬화 방식(안드로이드는 Parcelable 권장).

- **세부 설명**
  - 상황 설명  
    - 번들은 “경량·직렬화 가능한” 데이터만 담아야 한다.
  - 구체적인 동작/원리  
    - 기본형/문자열 계열: `boolean/int/long/float/double/String/CharSequence` 및 배열/ArrayList.  
    - 참조형: `Parcelable`, `Serializable`(권장X), `Bundle`, `SparseArray<Parcelable>`, `IBinder`(API 18+), `Size/SizeF` 등.
  - 예시 코드나 상황 예시
    ```kotlin
    out.putParcelable("profile", profileParcelable)
    out.putSparseParcelableArray("items", sparseArrayOf())
    ```

- **장점**
  - 플랫폼 호환이 좋다 (OS가 직렬화/역직렬화 경로를 제공).
  - 복원 속도가 좋다 (경량 데이터 즉시 재사용).

- **단점/주의점**
  - 대용량/이미지/바이너리는 안 좋다 (용량 제한/성능 저하).  
  - 커스텀 타입은 버전 호환이 안 좋다 (필드 변경 시 역직렬화 실패 가능 → 버전 전략 필요).

- **핵심 답변 요약**
  - 상황: 번들로 상태/인자 전달 필요  
  - 원인: 구성 변경/프로세스 사망 대비와 컴포넌트 간 통신  
  - 해결 방법: 기본형·문자열·`Parcelable` 중심으로 **작고 직렬화 가능한 데이터만** 저장

- **면접 대답용**
  > “번들은 기본형·문자열·`Parcelable` 같은 경량 데이터만 담아야 하고, 큰 덩어리는 DB/파일로 관리합니다.”


## Android에서 Parcelable와 Serializable의 차이점은 무엇이며, 각각을 사용할 때 어떤 상황에 유리한지 설명해주세요.
- **용어 설명**  
  - **Parcelable**: Android에서 객체를 직렬화하여 IPC(Inter-Process Communication)나 Activity/Fragment 간 데이터 전달 시 사용하는 인터페이스.  
  - **Serializable**: Java 표준 직렬화 방식. 객체를 바이트 스트림으로 변환하는 인터페이스.

- **세부 설명**  
  - Parcelable은 Android OS 최적화를 고려하여 만들어져, 더 빠르고 메모리 효율적임.  
  - Serializable은 구현이 간단하지만, 성능이 느리고 메모리 사용량이 많음.  
  - 예: 대량의 데이터 전송 시 Parcelable, 테스트나 임시 객체 저장 시 Serializable 사용 가능.

- **장점**
  - Parcelable: 빠르고 효율적 → Android IPC에 최적화.  
  - Serializable: 구현이 단순 → 코드 작성이 쉬움.

- **단점/주의점**
  - Parcelable: 구현 코드가 길고 복잡 → 실수 가능성 높음.  
  - Serializable: 느리고 메모리 사용량 높음 → 성능 저하 가능.

- **핵심 답변 요약**  
  - 상황: Activity 간 데이터 전달 필요.  
  - 원인: 직렬화 방식 선택.  
  - 해결: 성능 요구 시 Parcelable, 단순성 필요 시 Serializable.

- **면접 대답용**  
  > "Android에선 Parcelable이 성능이 좋아 IPC에 최적이고, Serializable은 구현은 쉽지만 느리기 때문에 주로 테스트나 간단한 데이터 전송에 씁니다."

## Parcelable 인터페이스를 구현할 때 주의해야 할 점과 Parcelable를 사용하는 이유에 대해 설명해주세요.
- **용어 설명**  
  - Parcelable: 객체를 Parcel 형태로 변환하여 Activity/Fragment 간 또는 프로세스 간 전송할 수 있게 하는 인터페이스.

- **세부 설명**  
  - Parcelable 구현 시 `writeToParcel()`과 `CREATOR` 객체 필수 구현.  
  - 필드 순서 유지, null 처리, 데이터 타입 일관성 보장이 중요.  
  - 사용하는 이유: 빠른 직렬화/역직렬화, Android IPC에 최적화.

- **장점**
  - 빠른 성능 → Android 내부 최적화 구조 사용.  
  - 메모리 효율적 → 불필요한 오브젝트 생성 최소화.

- **단점/주의점**
  - 구현 복잡 → 실수 시 런타임 에러 발생 가능.  
  - 버전 변경 시 호환성 문제 발생 가능.

- **핵심 답변 요약**  
  - 상황: 객체를 Intent로 전달.  
  - 원인: IPC 최적화 필요.  
  - 해결: Parcelable 구현, 필드 순서와 타입 주의.

- **면접 대답용**  
  > "Parcelable은 Android IPC에 최적화돼 빠르고 효율적이지만, 필드 순서와 null 처리를 잘못하면 역직렬화 에러가 납니다."

## Parcelable 인터페이스를 구현할 때 발생할 수 있는 실수나 주의해야 할 점에 대해 자세히 설명해주세요.
- **용어 설명**  
  - Parcelable: Android 데이터 직렬화 인터페이스.

- **세부 설명**  
  - 필드 순서 불일치 → 역직렬화 시 데이터 깨짐.  
  - null 값 처리 누락 → NullPointerException.  
  - CREATOR 구현 오류 → 객체 복원 실패.

- **장점**
  - 성능 최적화 가능 → 대용량 데이터 전달 시 유리.

- **단점/주의점**
  - 복잡한 구현 과정에서 버그 발생 확률 높음 → 테스트 필수.

- **핵심 답변 요약**  
  - 상황: Parcelable 구현.  
  - 원인: 순서/타입/CREATOR 오류.  
  - 해결: 순서 유지, null 처리, 유닛 테스트 수행.

- **면접 대답용**  
  > "순서나 타입이 맞지 않으면 역직렬화가 깨지기 때문에, Parcelable 구현 시 필드 순서와 타입 일관성을 꼭 지켜야 합니다."

## MVVM 아키텍처에서 모델과 뷰모델 사이의 의존성은 어떻게 관리해야 하나요?
- **용어 설명**

- **세부 설명**  
  - DI 프레임워크(Hilt, Dagger)로 의존성 주입.

- **장점**
  - 테스트 용이 → Mock 객체 주입 가능.

- **핵심 답변 요약**  
  - 상황: 모델-ViewModel 의존성 관리 필요.

## MVVM 아키텍처에서 뷰와 뷰모델 사이에는 어떤 관계가 있고, 이 관계를 어떻게 유지해야 할까요?
- **용어 설명**  
  - 뷰: UI 요소.  
  - 뷰모델: UI 상태와 이벤트 관리.

- **세부 설명**  
  - View는 ViewModel의 상태를 관찰(Observer).  
  - ViewModel은 View를 직접 참조하지 않음.

- **장점**
  - 결합도 낮음 → 재사용성 향상.  
  - UI 변경에도 로직 수정 최소화.

- **단점/주의점**
  - 상태 동기화 누락 시 UI 불일치.  
  - 잘못된 Observer 해제 관리 시 메모리 누수.

- **핵심 답변 요약**  
  - 상황: View-ViewModel 관계 설계.  
  - 원인: 결합도 낮추기.  
  - 해결: Observer 패턴 활용.

- **면접 대답용**  
  > "View는 ViewModel 상태를 관찰만 하고, ViewModel이 View를 직접 참조하지 않게 유지해야 합니다."

## 의존성 주입(Dependency Injection)이 MVVM 아키텍처에서 왜 중요한가요? 그리고 의존성 주입을 구현하기 위해 어떤 방법을 사용할 수 있을까요
- **용어 설명**  
  - **Dependency Injection(DI)**: 객체가 의존하는 다른 객체를 외부에서 주입받는 설계 패턴.
  - **MVVM**: Model-View-ViewModel 구조에서 ViewModel이 Model이나 Repository에 의존할 때, 결합도를 낮추기 위해 DI를 활용.

- **세부 설명**  
  - MVVM에서 ViewModel이 Repository나 UseCase에 직접 의존하면 테스트와 유지보수가 어려워짐.  
  - DI를 사용하면 객체 생성 책임을 외부로 분리하여, 모듈 교체나 테스트가 용이해짐.  
  - 구현 방법: Hilt, Dagger, Koin, Service Locator 등.

- **장점**
  - 결합도 감소 → 코드 변경 범위 축소.  
  - 테스트 용이 → Mock 객체 주입 가능.  
  - 재사용성 향상 → 다른 구현체로 쉽게 교체 가능.

- **단점/주의점**
  - 러닝 커브 → 프레임워크 학습 필요.  
  - 구성 복잡 → 잘못된 설정 시 런타임 에러.

- **핵심 답변 요약**  
  - 상황: MVVM에서 객체 간 결합도 낮추기.  
  - 원인: 유지보수성과 테스트성 향상 필요.  
  - 해결: Hilt/Dagger/Koin 등을 활용한 DI 적용.

- **면접 대답용**  
  > "MVVM에서 DI는 ViewModel이 Model에 강하게 묶이지 않게 해 테스트와 유지보수가 쉬워집니다. Hilt나 Dagger를 주로 사용하죠."

## Dagger와 Hilt의 차이점은 무엇이고, 각각을 선택할 때 고려해야 할 사항은 무엇인가요?
- **용어 설명**  
  - **Dagger**: 컴파일 타임 의존성 주입 프레임워크.  
  - **Hilt**: Dagger 기반의 Android 전용 DI 프레임워크.

- **세부 설명**  
  - Dagger: 유연성과 확장성이 높지만, 초기 설정이 복잡.  
  - Hilt: Dagger의 복잡한 설정을 줄이고 Android 라이프사이클과 연동.

- **장점**
  - Dagger: 높은 확장성, 세밀한 제어 가능.  
  - Hilt: 빠른 설정, 라이프사이클 자동 관리.

- **단점/주의점**
  - Dagger: 진입 장벽 높음.  
  - Hilt: Dagger보다 커스터마이징 제한.

- **핵심 답변 요약**  
  - 상황: DI 프레임워크 선택.  
  - 원인: 프로젝트 요구사항에 따른 선택.  
  - 해결: 확장성 필요 → Dagger, 빠른 개발 → Hilt.

- **면접 대답용**  
  > "Dagger는 자유도가 높지만 복잡하고, Hilt는 간단하지만 제약이 있어요. Android라면 Hilt가 개발 속도에 유리합니다."

---

## Hilt를 주로 사용하는 이유는 무엇이며, Dagger와 비교했을 때 어떤 장단점이 있을까요?
- **용어 설명**  
  - Hilt: Dagger를 기반으로 Android 개발 최적화.

- **세부 설명**  
  - Dagger의 복잡한 설정을 줄이고, Android 컴포넌트(LifecycleOwner)에 맞춘 주입 기능 제공.

- **장점**
  - 설정 간단 → 보일러플레이트 코드 감소.  
  - 라이프사이클 자동 관리 → Activity/Fragment에 쉽게 주입.

- **단점/주의점**
  - 유연성 제한 → 복잡한 커스터마이징 어려움.  
  - Dagger 고급 기능 일부 사용 불가.

- **핵심 답변 요약**  
  - 상황: Android DI 적용.  
  - 원인: 개발 속도 향상 필요.  
  - 해결: Hilt 사용.

- **면접 대답용**  
  > "Hilt는 설정이 간단하고 Android 라이프사이클에 맞춰서 주입되지만, 복잡한 구조를 구현할 땐 Dagger가 유리할 수 있습니다."

## Hilt가 Dagger보다 간단한 점은 어떤 측면에서 나타나는 것이며, 간단함으로 인해 어떠한 제약이 있을 수 있을까요?
- **용어 설명**  
  - Hilt: Dagger의 설정을 간소화한 DI 프레임워크.

- **세부 설명**  
  - 모듈과 컴포넌트의 수동 연결을 자동 처리.  
  - AndroidEntryPoint, InstallIn 어노테이션으로 주입 범위 지정.

- **장점**
  - 설정 단순화 → 진입 장벽 낮음.  
  - 개발 시간 단축.

- **단점/주의점**
  - 커스터마이징 제약 → 복잡한 스코프 구성 어려움.  
  - 특정 상황(Dynamic Feature Module)에서 제약 존재.

- **핵심 답변 요약**  
  - 상황: DI 간소화 필요.  
  - 원인: 보일러플레이트 코드 감소.  
  - 해결: Hilt 사용, 제약은 설계 시 고려.

- **면접 대답용**  
  > "Hilt는 설정이 단순해 빠르게 개발할 수 있지만, 복잡한 스코프나 모듈 구성은 Dagger만큼 자유롭지 않습니다."

---

## 의존성 주입에서 provider를 간략화하는 과정에서 발생할 수 있는 잠재적인 문제는 무엇일까요? 이러한 문제를 해결하기 위해 어떤 방법을 사용할 수 있을까요?
- **용어 설명**  
  - Provider: 필요 시점에 객체를 생성해 주는 Dagger/Hilt 기능.

- **세부 설명**  
  - Provider 간략화 시 생성 타이밍과 라이프사이클을 잘못 설정하면 메모리 누수나 예기치 못한 동작 발생.

- **장점**
  - 지연 생성 → 성능 최적화 가능.

- **단점/주의점**
  - 생성 시점 예측 어려움 → 디버깅 어려움.  
  - 스코프와 불일치 시 메모리 누수.

- **핵심 답변 요약**  
  - 상황: Provider 단순화.  
  - 원인: 객체 생성 타이밍 잘못 관리.  
  - 해결: 스코프 명확히 지정, Lazy/Provider 적절히 사용.

- **면접 대답용**  
  > "Provider를 단순화하면 생성 타이밍 예측이 힘들 수 있어, 스코프와 Lazy 사용을 명확히 관리해야 합니다."

## provider 함수의 반환 타입을 지정하는 것이 왜 중요한가요? 타입을 지정하지 않았을 때 발생할 수 있는 잠재적인 문제는 무엇이 있을까요?
- **용어 설명**  
  - Provider 함수: DI 모듈에서 객체 생성 후 반환하는 함수.

- **세부 설명**  
  - 반환 타입 미지정 시, 의도치 않은 객체나 서브클래스가 주입될 수 있음.

- **장점**
  - 타입 안전성 확보 → 런타임 오류 방지.

- **단점/주의점**
  - 타입 미지정 → 디버깅 어려움, 예기치 않은 동작.

- **핵심 답변 요약**  
  - 상황: Provider 구현.  
  - 원인: 타입 미지정.  
  - 해결: 반환 타입 명시.

- **면접 대답용**  
  > "Provider 반환 타입을 명시하면 타입 안전성이 확보돼 런타임 오류를 줄일 수 있습니다."

---

## DI에서 인터페이스 자체를 반환하는 것이 아닌 구현체를 반환해야 하는 이유는 무엇일까요? 인터페이스를 반환하는 것이 가지는 잠재적인 문제는 무엇일까요?
- **용어 설명**  
  - 인터페이스 반환: DI 모듈에서 Interface 타입을 리턴.

- **세부 설명**  
  - 인터페이스만 반환하면, Hilt/Dagger가 실제 구현체를 찾기 위해 바인딩을 요구.  
  - 구현체를 반환하면 명확히 주입 가능.

- **장점**
  - 구현체 반환 → 설정 명확, 주입 안정성.

- **단점/주의점**
  - 인터페이스 반환 시 바인딩 누락 가능.

- **핵심 답변 요약**  
  - 상황: DI 제공 타입 결정.  
  - 원인: 구현체 주입 안정성 확보 필요.  
  - 해결: 구현체 반환.

- **면접 대답용**  
  > "DI 모듈에서 구현체를 반환하면 주입이 명확해지고, 인터페이스만 반환하면 바인딩 누락으로 에러가 날 수 있습니다."

## DI에서 인터페이스를 사용하는 장점은 무엇이며, DI에서는 주로 어떤 상황에서 인터페이스를 사용하나요?
- **용어 설명**  
  - 인터페이스: 구현을 숨기고 규약만 정의하는 타입.

- **세부 설명**  
  - 구현체 변경 시 인터페이스를 통한 결합도 감소.  
  - 테스트 시 Mock/Fake 객체로 교체 용이.

- **장점**
  - 유연성 → 구현체 교체 쉬움.  
  - 테스트 용이성 향상.

- **단점/주의점**
  - 불필요한 추상화 → 과도한 복잡성.

- **핵심 답변 요약**  
  - 상황: 유연한 설계 필요.  
  - 원인: 구현체 교체/테스트 용이성.  
  - 해결: 인터페이스 활용.

- **면접 대답용**  
  > "DI에서 인터페이스는 구현체 교체와 테스트 용이성을 위해 사용하며, 주로 Repository, UseCase 계층에 적용합니다."

## MVVM을 클린 아키텍처와 함께 사용할 때의 장점은 무엇인가요?
- **용어 설명**  
  - **MVVM**: View, ViewModel, Model로 역할을 분리하는 패턴.  
  - **Clean Architecture**: 계층 간 의존성을 안쪽으로만 흐르게 하여 변경에 강한 구조를 만드는 설계 원칙.

- **세부 설명**  
  - MVVM은 UI와 로직을 분리하고, Clean Architecture는 비즈니스 로직을 중심으로 계층을 나눔.  
  - 둘을 결합하면 UI 변경과 비즈니스 로직 변경이 서로 영향을 최소화.

- **장점**  
  - 유지보수 용이 → UI 변경 시 비즈니스 로직 수정 최소화.  
  - 테스트 용이 → 각 계층 단위 테스트 가능.  
  - 확장성 → 기능 확장 시 구조 변경 최소화.

- **단점/주의점**  
  - 초기 설계 복잡 → 구조 이해와 설계 시간이 필요.  
  - 계층 분리 과도 시 개발 속도 저하.

- **핵심 답변 요약**  
  - 상황: UI와 로직 분리 + 계층 구조 안정성 확보.  
  - 원인: 유지보수성과 확장성 확보 필요.  
  - 해결: MVVM + Clean Architecture 결합.

- **면접 대답용**  
  > "MVVM과 Clean Architecture를 같이 쓰면 UI와 비즈니스 로직을 확실히 분리해 유지보수와 테스트가 쉬워집니다."

---

## Clean Architecture에서 각 계층간의 의존성은 어떻게 관리되어야 하며, 이를 통해 어떤 장점이 얻어질 수 있을까요?
- **용어 설명**  
  - 계층: Entity, UseCase, Interface Adapter, Framework & Driver.

- **세부 설명**  
  - 의존성은 안쪽(비즈니스 로직)으로만 향해야 함.  
  - DIP(Dependency Inversion Principle)를 적용하여 내부 계층이 외부 구현체에 의존하지 않도록 설계.

- **장점**  
  - 변경에 강함 → UI, DB 변경에도 핵심 로직 영향 최소화.  
  - 테스트 용이 → 외부 의존성 없이 핵심 로직 테스트 가능.

- **단점/주의점**  
  - 인터페이스/추상화 많아져 복잡도 상승.  
  - 러닝 커브 존재.

- **핵심 답변 요약**  
  - 상황: 계층 간 결합도 최소화 필요.  
  - 원인: 변경에 강한 구조 필요.  
  - 해결: 의존성 안쪽으로만 흐르게 설계.

- **면접 대답용**  
  > "Clean Architecture는 의존성을 안쪽으로만 두어 UI나 DB 변경에도 비즈니스 로직이 안전하게 유지됩니다."

---

## Clean Architecture에서의 UseCase는 어떤 역할을 하며, 어떤 이점을 제공하나요?
- **용어 설명**  
  - UseCase: 애플리케이션의 비즈니스 규칙을 실행하는 인터랙터 역할.

- **세부 설명**  
  - ViewModel 등 외부 계층에서 요청을 받아 비즈니스 로직을 수행하고 결과 반환.

- **장점**  
  - 로직 재사용 가능.  
  - 테스트 용이 → 독립적으로 단위 테스트 가능.  
  - UI와 로직의 완전한 분리.

- **단점/주의점**  
  - UseCase 남용 시 계층 복잡도 증가.

- **핵심 답변 요약**  
  - 상황: 비즈니스 로직 중앙 집중 필요.  
  - 원인: UI 독립성 확보.  
  - 해결: UseCase를 통해 로직 관리.

- **면접 대답용**  
  > "UseCase는 비즈니스 로직을 담당해 UI와 독립성을 보장하고 테스트를 쉽게 합니다."

## Clean Architecture에서의 Repository는 어떤 역할을 하며, 왜 사용하는 것이 좋은가요?
- **용어 설명**  
  - Repository: 데이터 소스(DB, API 등)를 추상화하여 UseCase에 제공.

- **세부 설명**  
  - 데이터 접근 로직을 캡슐화해 구현체 변경에 유연.

- **장점**  
  - 데이터 소스 교체 용이.  
  - 테스트 시 Mock 데이터 주입 가능.  
  - 중복 코드 감소.

- **단점/주의점**  
  - 불필요한 추상화 가능성.

- **핵심 답변 요약**  
  - 상황: 데이터 접근 관리 필요.  
  - 원인: 유연성과 테스트성 확보.  
  - 해결: Repository 패턴 사용.

- **면접 대답용**  
  > "Repository는 데이터 소스를 숨겨서 변경에 강하고, 테스트에 유리합니다."

## Clean Architecture에서 UseCase와 Repository 간의 관계는 어떻게 설계되어야 하며, 이를 통해 어떤 장점을 얻을 수 있을까요?
- **용어 설명**  
  - UseCase ↔ Repository: 비즈니스 로직 ↔ 데이터 접근 계층.

- **세부 설명**  
  - UseCase는 Repository 인터페이스에 의존.  
  - 구현체는 데이터 계층에서 제공.

- **장점**  
  - 느슨한 결합 → 데이터 소스 변경에 유연.  
  - 테스트 용이 → Mock Repository 사용 가능.

- **단점/주의점**  
  - 인터페이스 과다 생성 가능.

- **핵심 답변 요약**  
  - 상황: 데이터 접근 로직 변경 가능성 존재.  
  - 원인: 결합도 최소화.  
  - 해결: 인터페이스 기반 의존성 주입.

- **면접 대답용**  
  > "UseCase는 Repository 인터페이스에 의존해 데이터 소스를 쉽게 교체할 수 있습니다."

## MVVM 패턴에서의 의존성 주입은 어떻게 구현하나요?
- **용어 설명**  
  - MVVM: View ↔ ViewModel ↔ Model 구조.  
  - DI: 의존 객체를 외부에서 생성해 주입.

- **세부 설명**  
  - Hilt/Dagger를 사용해 ViewModel, Repository, UseCase 주입.

- **장점**  
  - 결합도 감소.  
  - 테스트 용이.

- **단점/주의점**  
  - 설정 복잡도 존재.

- **핵심 답변 요약**  
  - 상황: MVVM에서 의존성 관리 필요.  
  - 원인: 유지보수와 테스트성 향상.  
  - 해결: DI 프레임워크 사용.

- **면접 대답용**

## MVVM 패턴에서의 DI가 어떻게 유지보수성 및 테스트 용이성에 도움을 주는지 설명해주세요.
- **세부 설명**

  - 해결: DI로 의존성 주입.

- **면접 대답용**

## DI를 통해 객체를 주입받을 때 싱글톤으로 설정하는 방법과 일반 객체로 설정하는 방법에 대해 설명해주세요.
- **용어 설명**  
  - Singleton: 앱 생명주기 동안 한 인스턴스만 존재.  
  - 일반 객체: 필요 시마다 새로 생성.

- **세부 설명**  
  - Hilt/Dagger에서 `@Singleton` 어노테이션 사용.  
  - 일반 객체는 스코프 없이 주입.

- **장점**  
  - Singleton: 메모리 절약, 상태 공유 가능.  
  - 일반 객체: 독립성 보장, 상태 충돌 방지.

- **단점/주의점**  
  - Singleton: 상태 관리 부주의 시 버그 발생.  
  - 일반 객체: 생성 비용 증가.

- **핵심 답변 요약**  
  - 상황: 객체 생명주기 결정 필요.  
  - 원인: 메모리/상태 관리 고려.  
  - 해결: 상황에 맞는 스코프 지정.

- **면접 대답용**  
  > "싱글톤은 상태 공유가 필요할 때, 일반 객체는 독립 인스턴스가 필요할 때 사용합니다."

## DI를 사용하여 싱글톤 객체를 주입 받을 때 생기는 잠재적인 문제점에 대해 설명해주세요.
- **세부 설명**  
  - 전역 상태 공유로 인한 예기치 않은 부작용.  
  - 테스트 간 상태가 누적되어 오작동 가능.

- **장점**  
  - 없음(문제 상황 설명이므로).

- **단점/주의점**  
  - 상태 관리 어려움.  
  - 예측 불가능한 버그 발생.

- **핵심 답변 요약**  
  - 상황: Singleton 주입.  
  - 원인: 전역 상태 공유.  
  - 해결: 상태 초기화, 불변 객체 사용.

- **면접 대답용**  
  > "싱글톤은 상태 공유로 인해 예기치 않은 버그를 만들 수 있어, 상태 초기화나 불변 객체로 관리해야 합니다."

## DI를 통해 객체를 주입 받을 때 싱글톤으로 설정되지 않아야 하는 상황에서 어떻게 처리하는 것이 좋을지에 대해 설명해주세요.
- **세부 설명**  
  - 사용자 세션, 요청 단위 데이터 등은 싱글톤 사용 부적합.  
  - `@Reusable`, `@ActivityScoped` 등 적절한 스코프 사용.

- **장점**  
  - 필요에 맞는 객체 생명주기 관리 가능.

- **단점/주의점**  
  - 잘못된 스코프 선택 시 메모리 낭비.

- **핵심 답변 요약**
