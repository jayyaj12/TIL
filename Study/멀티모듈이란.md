# 멀티모듈

## 1. 개념
멀티모듈 아키텍처는 하나의 앱을 여러 Gradle 모듈로 나누어 **책임을 분리**하고, **빌드·테스트·배포 단위를 세분화**하는 방식입니다.

**핵심 아이디어**
- 기능·레이어별 경계를 명확히 하고, 의존 방향을 통제해 결합도를 낮춤
- 공통 로직/의존성은 중앙에서 관리하고, 모듈은 필요한 것만 의존

---

## 2. 도입 배경
- **빌드 효율**: 변경 영향 범위를 축소해 증분 빌드 최적화, 병렬 빌드 활용
- **변경 내성**: UI/데이터/도메인 변경의 파급을 최소화
- **협업 확장성**: 팀 단위로 모듈 책임을 나눠 독립 개발·배포 가능
- **테스트 용이성**: 도메인/데이터/프레젠테이션 단위로 격리 테스트

---

## 3. 프로젝트 예시 구조
### 모듈 구성
- `:presentation` — 화면, ViewModel, UI 상태/이벤트, Hilt 진입점
- `:domain` — 비즈니스 규칙: entities, usecases, repositories(인터페이스)
- `:data` — 외부 연동: Retrofit/Room/Paging, DTO/엔티티, Repository 구현, 매퍼

### 의존 관계 (본 프로젝트)
```
:presentation → :domain
:presentation → :data
:data → :domain
```
> 실무 팁: 엄밀한 클린 규칙은 `:presentation` ↛ `:data` 지향이지만, 본 프로젝트는 DI/구현 편의상 `:data`도 의존. 대신 UI에서는 도메인 타입만 사용해 결합을 낮춤.

## 4. 실전 적용 상세

### 4.1 모듈 선언
`settings.gradle.kts`
```kotlin
rootProject.name = "My Application"
include(":presentation")
include(":domain")
include(":data")
```

### 4.2 버전/의존성 중앙관리
`gradle/libs.versions.toml`에서 `bundles` 정의
```toml
[bundles]
androidx-core = ["androidx-core-ktx","androidx-appcompat","material"]
network = ["retrofit","retrofit-serialization","serialization-json","okhttp","okhttp-logging"]
room = ["androidx-room-runtime","androidx-room-ktx"]
paging = ["androidx-paging-runtime","androidx-paging-runtime-ktx"]
```
**효과**
- **중복 제거**: 모듈별 dependencies가 간결
- **일관성**: 버전/라이브러리 변경을 중앙에서 통제

### 4.3 도메인 계층 (`:domain`)
- 순수 코틀린, 외부 프레임워크 미의존
- 예: `SearchVideoUseCase`, `AddFavoriteVideoUseCase`, `ObserveFavoriteVideoUseCase`, `DeleteFavoriteVideoUseCase`, `VideoRepository` 인터페이스

### 4.4 데이터 계층 (`:data`)
- 외부 연동과 매핑 책임
  - API: `VideoApi` (Retrofit)
  - 로컬: `AppDatabase`, `VideoDao` (Room)
  - 매퍼: DTO/DB ↔ 도메인 변환
  - 저장소: `VideoRepositoryImpl`이 `VideoRepository` 구현
- Paging 연계: `Pager + PagingSource`로 스트림 노출

### 4.5 프레젠테이션 계층 (`:presentation`)
- ViewModel에서 유즈케이스 호출
- 상태: StateFlow, 이벤트: SharedFlow
- 화면: Fragment/Activity에서 `repeatOnLifecycle`로 안전 수집
- Hilt 모듈에서 인터페이스-구현 결선 (`RepositoryModule`)

### 4.6 모듈별 의존성 선언 예시
#### `presentation/build.gradle.kts`
```kotlin
dependencies {
    implementation(project(":domain"))
    implementation(project(":data"))

    implementation(libs.bundles.room)
    kapt(libs.androidx.room.compiler)

    implementation(libs.bundles.paging)
    implementation(libs.bundles.network)
    implementation(libs.bundles.androidx.core)

    implementation(libs.androidx.viewpager2)
    implementation(libs.androidx.activity)
    implementation(libs.androidx.lifecycle.viewmodel)
    implementation(libs.androidx.constraintlayout)
    implementation(libs.androidx.fragment)

    implementation(libs.hilt.android)
    kapt(libs.hilt.compiler)
    implementation(libs.glide)
    implementation(libs.timber)
}
```

#### `data/build.gradle.kts`
```kotlin
dependencies {
    implementation(project(":domain"))

    implementation(libs.bundles.room)
    implementation(libs.androidx.room.paging)
    kapt(libs.androidx.room.compiler)

    implementation(libs.bundles.paging)
    implementation(libs.bundles.network)
    implementation(libs.bundles.androidx.core)

    implementation(libs.hilt.android)
    kapt(libs.hilt.compiler)
    implementation(libs.timber)
}
```

## 5. 장단점

**장점**
- 빌드 성능: 증분/병렬 빌드로 속도 향상
- 경계 명확: 책임 분리로 가독성·확장성·리팩터링 용이
- 테스트 용이: 모듈별 유닛/통합 테스트 가능
- 협업 효율: 팀/기능별 독립 개발·리뷰·릴리스
- 재사용성: 공통 코드 모듈화 가능

**단점**
- 복잡도 증가: 모듈 수·의존 규칙 관리 필요
- 보일러플레이트: 인터페이스/매퍼/DI 구성 추가
- DI/컴포넌트 경계 고려: @InstallIn 레벨, 순환 참조 예방
- 규칙 일탈 위험: 잘못된 참조로 아키텍처 무너질 수 있음

---

## 6. 도입 체크리스트
- 경계 정의: 각 모듈의 책임과 공개 API 명확화
- 의존 방향: 안쪽(도메인)으로만 향하는지 검토
- 도메인 순수성: Android/네트워크/DB 타입 미의존
- 모델 분리: DTO/DB/도메인/UI 모델 분리 및 매퍼 준비
- 버전 중앙화: libs.versions.toml + bundles 활용
- 테스트 전략: 모듈별 유닛/통합 테스트 기준 수립

---

## 7. 마이그레이션 팁
- 작은 단위부터 분리: 공통/도메인 → 데이터 → 프레젠테이션 순
- 의존성 역전부터 구현: 인터페이스는 domain, 구현은 data
- DI 모듈에서 결선 집중 관리
- 점진적 접근: 빌드 스크립트와 버전 카탈로그부터 정리
