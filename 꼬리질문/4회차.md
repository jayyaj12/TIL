### [코틀린에서 인터페이스와 클래스의 차이를 설명하시오]
- **용어 설명**
  - **인터페이스**: 객체의 행위 계약을 정의하며 상태(백킹 필드)는 가질 수 없음. 추상 메서드와 디폴트 메서드(기본 구현)를 정의 가능.
  - **클래스**: 상태(프로퍼티+백킹 필드)를 가지며 구체적인 동작을 구현. 생성자와 초기화 블록을 가질 수 있음.

- **세부 설명**
  - 상황 설명: 상태가 필요한 객체인지, 계약만 필요한지에 따라 선택.
  - 구체적인 동작/원리:
    - 인터페이스: 생성자가 없으며, 프로퍼티는 추상 또는 커스텀 getter만 가능.
    - 클래스: 상태 저장, 생성자, 상속(`open` 필요) 가능.
  - 예시 코드
    ```kotlin
    interface Drivable {
        fun drive()
    }
    open class Vehicle(val name: String)
    class Car(name: String) : Vehicle(name), Drivable {
        override fun drive() = println("$name is driving")
    }
    ```

- **장점**
  - 인터페이스: 다중 구현 가능, 설계 유연성, 테스트 용이성.
  - 클래스: 상태 관리 가능, 명확한 구현체 제공.

- **단점/주의점**
  - 인터페이스: 상태 저장 불가.
  - 클래스: 단일 상속만 가능.

- **핵심 답변 요약**
  - 상황: 객체 설계 시 상태 필요 여부 판단.
  - 원인: 인터페이스는 계약, 클래스는 상태+구현.
  - 해결 방법: 상태 없는 공통 행위는 인터페이스, 상태 있는 경우 클래스 사용.

- **면접 대답용**
  > "인터페이스는 상태 없이 계약과 기본 구현을 제공하고, 클래스는 상태와 생성자를 가집니다."

### [코틀린에서 한 클래스가 여러 개의 인터페이스를 구현할 수 있는데, 이때 인터페이스간에 충돌이 일어날 경우 어떻게 해결할 수 있나요?]
- **용어 설명**
  - **충돌**: 여러 인터페이스에서 동일한 시그니처의 디폴트 메서드를 제공할 때 모호성이 발생하는 상황.

- **세부 설명**
  - 상황 설명: 한 클래스가 여러 인터페이스를 구현하고, 같은 이름/파라미터의 디폴트 메서드가 있는 경우.
  - 구체적인 동작/원리:
    - 반드시 구현 클래스에서 `override` 해야 함.
    - `super<인터페이스>.메서드()`로 특정 구현 호출 가능.
  - 예시 코드
    ```kotlin
    interface A { fun speak() { println("A") } }
    interface B { fun speak() { println("B") } }
    class C : A, B {
        override fun speak() {
            super<A>.speak()
        }
    }
    ```

- **장점**
  - 모호성 명시적으로 해소 가능.
  - 필요에 따라 두 구현을 조합 가능.

- **단점/주의점**
  - override 필수.
  - 코드 가독성이 떨어질 수 있음.

- **핵심 답변 요약**
  - 상황: 동일 시그니처 메서드 충돌.
  - 원인: 다중 구현으로 인한 모호성.
  - 해결 방법: override + `super<인터페이스>`로 특정 구현 호출.

- **면접 대답용**
  > "충돌 시 반드시 override해야 하고, `super<인터페이스>`로 원하는 구현을 선택합니다."

### [코틀린에서 클래스가 다중 인터페이스를 구현할 때 생기는 다이아몬드 문제는 어떻게 해결할 수 있나요?]
- **용어 설명**
  - **다이아몬드 문제**: 상위 인터페이스를 여러 경로로 상속받아 동일 메서드가 중복되는 상황.

- **세부 설명**
  - 상황 설명: 두 인터페이스가 같은 상위 인터페이스를 구현하는 경우.
  - 구체적인 동작/원리:
    - Kotlin은 충돌 발생 시 override를 강제해 모호성 제거.
  - 예시 코드
    ```kotlin

            super<Left>.action()
        }
    }
    ```

- **장점**
  - 컴파일 타임에 모호성 해소.
  - 명시적 선택 가능.

- **단점/주의점**
  - 선택 로직이 복잡할 수 있음.

- **핵심 답변 요약**
  - 상황: 다중 경로 상속.
  - 원인: 공통 상위의 메서드 중복.
  - 해결 방법: override로 명시적 선택.

- **면접 대답용**
  > "Kotlin은 다중 인터페이스 충돌 시 override를 강제해 다이아몬드 문제를 컴파일 시 해결합니다."

- **용어 설명**
  - **충돌**: 여러 경로에서 동일 메서드 구현이 상속될 때 발생하는 모호성.

- **세부 설명**
  - 상황 설명: 다중 인터페이스 구현 시 같은 시그니처의 default 메서드가 존재하면 충돌 발생.
  - 구체적인 동작/원리:
    - 반드시 구현 클래스에서 override하여 어떤 구현을 사용할지 명시.
  - 예시 코드나 상황 예시
    ```kotlin
    interface X { fun action() { println("X") } }
    interface Y { fun action() { println("Y") } }
    class Z : X, Y {
        override fun action() { super<X>.action() }
    }
    ```

- **장점**
  - 충돌 시 의도를 명확하게 표현 가능.

- **단점/주의점**
  - override 필수.
  - 코드가 장황해질 수 있음.

- **핵심 답변 요약**
  - 상황: 다중 경로로 동일 메서드 상속.
  - 원인: 메서드 모호성.
  - 해결 방법: override + super<인터페이스>로 선택.

- **면접 대답용**
  > "다중 인터페이스에서 동일 메서드가 겹치면 override하고 super<인터페이스>로 구현을 선택해야 합니다."

### [자바에서 인터페이스를 구현한 다중 클래스가 있을 때, 이 다중 클래스들이 모두 같은 인터페이스 메서드를 구현하더라도 각각의 클래스에서 구현한 방식이 다를 경우 이것이 어떤 디자인 패턴에 해당하며, 어떤 장점이 있을까요?]
- **용어 설명**
  - **Strategy 패턴**: 동일한 인터페이스로 다양한 동작을 정의하고 실행 시점에 교체 가능하게 하는 패턴.

  - 유연성: 런타임 구현 교체.

- **핵심 답변 요약**
  - 상황: 동일 계약 다른 구현 필요.
  - 원인: 동작 다양성.
  - 해결 방법: Strategy 패턴 사용.

- **면접 대답용**

### [리사이클러뷰의 뷰홀더 패턴과 뷰 재활용에 대해 설명하시오.]
- **용어 설명**
  - ViewHolder 패턴: findViewById/바인딩 비용을 캐싱해 스크롤 성능을 높이는 패턴.
  - 재활용: 스크롤로 화면 밖으로 나간 뷰를 풀에 담아 재사용.

- **세부 설명**
  - 상황 설명  
    - 긴 리스트에서 생성/바인딩 비용을 최소화해야 함.
  - 구체적인 동작/원리  
    - `onCreateViewHolder`에서 아이템 뷰 1회 생성 → 홀더에 참조 보관.  
    - `onBindViewHolder`에서 데이터만 교체.  
    - `getItemViewType`으로 이질적 레이아웃 혼재 시 재활용 풀 분리.
  - 예시 코드나 상황 예시
    ```kotlin
    class PostAdapter : ListAdapter<Post, VH>(DIFF) {
        override fun onCreateViewHolder(p: ViewGroup, vt: Int) =
            VH(ItemPostBinding.inflate(LayoutInflater.from(p.context), p, false))
        override fun onBindViewHolder(h: VH, pos: Int) = h.bind(getItem(pos))
        companion object {
            private val DIFF = object : DiffUtil.ItemCallback<Post>() {
                override fun areItemsTheSame(a: Post, b: Post) = a.id == b.id
                override fun areContentsTheSame(a: Post, b: Post) = a == b
            }
        }
    }
    class VH(private val b: ItemPostBinding): RecyclerView.ViewHolder(b.root) {
        fun bind(item: Post){ b.title.text = item.title }
    }
    ```

- **장점**
  - 스크롤 성능↑, GC↓, 배터리·발열↓.
  - 다양한 뷰타입을 안전하게 처리.

- **단점/주의점**
  - 상태 재사용 버그(체크박스, 애니메이션 잔상) 발생 가능.
  - 불변 데이터 원칙을 지키지 않으면 DiffUtil 최적화 실패.

- **핵심 답변 요약**
  - 상황: 대규모 리스트 성능 문제  
  - 원인: 반복 inflate/findViewById 비용  
  - 해결: ViewHolder 캐시 + DiffUtil로 최소 작업만 수행

- **면접 대답용**
  > “`onCreateViewHolder`는 1회 생성, `onBind`에서 데이터만 교체하고, 상태는 모델 기준으로 리셋합니다. 타입 분리는 `getItemViewType`으로 재활용 풀을 나눠 스크롤 품질을 확보합니다.”

    - 재활용 시 리스너·코루틴·이미지 로딩 정리가 필요.
  - 구체적인 동작/원리  
    - `onViewRecycled(holder)`: 이미지 로더 `clear()`, 애니메이션 cancel.  
    - Fragment 바인딩은 `onDestroyView`에서 null.  
    - 코루틴은 `repeatOnLifecycle`/`viewLifecycleOwner.lifecycleScope` 사용.  
    - `Context`는 `itemView.context`를 즉시 사용하고 저장하지 않음.
  - 예시 코드나 상황 예시
    ```kotlin
    override fun onViewRecycled(holder: VH) {
        super.onViewRecycled(holder)
        Glide.with(holder.itemView).clear((holder.binding.imageView))
        holder.binding.root.setOnClickListener(null)
    }
    ```

- **장점**
  - 누수 예방으로 OOM·프리즈 감소.
  - 재활용 품질 향상.

- **단점/주의점**
  - 클린업 누락 지점이 다양 → 체크리스트/리뷰 필요.

- **핵심 답변 요약**
  - 상황: 재활용 시 남는 리소스  
  - 원인: 이벤트/이미지/애니메이션 미정리  
  - 해결: `onViewRecycled`에서 일괄 정리, 바인딩 null, 컨텍스트 보관 금지

- **면접 대답용**
  > “재활용 훅에서 이미지·리스너를 해제하고, Fragment 바인딩은 `onDestroyView`에 null 처리합니다. 컨텍스트·액티비티 참조는 저장하지 않고 즉시 사용 원칙을 지킵니다.”


### [안드로이드에서 메모리 누수를 디버깅하고 해결하는 방법에 대해 어떤 경험이 있나요?]

  - Heap dump: 메모리 스냅샷 파일.

  - 예시 코드나 상황 예시

- **핵심 답변 요약**
  - 상황: 화면 종료 후 메모리 잔존

### [DiffUtil 클래스를 사용하는데 있어서 주의해야 할 점이나 고려해야 할 사항은 무엇인가요?]
- **용어 설명**
  - DiffUtil: 리스트 변경점을 계산해 최소한의 업데이트로 UI를 갱신하는 유틸.

- **세부 설명**
  - 상황 설명  
    - 대용량 리스트의 효율적 갱신 필요.
  - 구체적인 동작/원리  
    - `areItemsTheSame`: 항등성(고유 ID) 비교.  
    - `areContentsTheSame`: 내용 동등성(모든 필드) 비교.  
    - Payload를 활용해 부분 바인딩으로 잔상/깜빡임 최소화.
  - 예시 코드나 상황 예시
    ```kotlin
    data class Post(val id: Long, val title: String, val liked: Boolean)

    object PostDiff : DiffUtil.ItemCallback<Post>() {
        override fun areItemsTheSame(a: Post, b: Post) = a.id == b.id
        override fun areContentsTheSame(a: Post, b: Post) = a == b
        override fun getChangePayload(a: Post, b: Post): Any? =
            mutableSetOf<String>().apply {
                if (a.title != b.title) add("title")
                if (a.liked != b.liked) add("liked")
            }.ifEmpty { null }
    }

    override fun onBindViewHolder(h: VH, pos: Int, payloads: MutableList<Any>) {
        if (payloads.isEmpty()) return super.onBindViewHolder(h, pos, payloads)
        val diffs = payloads.last() as Set<String>
        val item = getItem(pos)
        if ("title" in diffs) h.binding.title.text = item.title
        if ("liked" in diffs) h.binding.likeBtn.isSelected = item.liked
    }
    ```

- **장점**
  - 최소 변경만 반영 → 성능·배터리·애니메이션 품질 향상.
  - 페이로드로 미세 업데이트 가능.

- **단점/주의점**
  - 잘못된 `areItemsTheSame`는 아이템 점프/깜빡임 유발.
  - 동등성 비교 비용이 높으면 계산 지연 → 키만 비교하고, 내용은 `==`/hash로 최적화.

- **핵심 답변 요약**
  - 상황: 리스트 변경 최적화 필요  
  - 원인: 전체 `notifyDataSetChanged`는 비효율  
  - 해결: 고유 ID 기반 항등성 + 페이로드 부분 바인딩으로 미세 갱신

- **면접 대답용**
  > “DiffUtil은 `areItemsTheSame`에 고유 ID를, `areContentsTheSame`엔 데이터 동등성을 사용합니다. 페이로드로 변경 필드만 바인딩해 깜빡임을 줄였고, 잘못된 비교로 인한 점프를 방지했습니다.”

### [고유한 식별자를 사용하지 않고 DiffUtil을 구현했을 때 어떤 문제가 발생할 수 있나요? 앱의 성능이나 안정성에 어떤 영향을 미칠 수 있을까요?]
- **용어 설명**
  - 고유 식별자(ID): 각 아이템을 유일하게 구분하는 키(예: DB PK, UUID).
  - DiffUtil: 두 리스트 차이를 계산해 필요한 부분만 갱신하는 유틸리티.

- **세부 설명**
  - 상황 설명  
    - 리스트 아이템에 고유 ID 없이 `equals`만으로 동일성/동등성 판단을 시도.
  - 구체적인 동작/원리  
    - `areItemsTheSame`에서 ID가 없으면 위치/내용 비교에 의존 → 아이템 이동·삽입·삭제가 오판.  
    - 동일 아이템을 다른 인스턴스로 받는 경우 매번 새로운 것으로 간주 → 전체 바인딩/애니메이션 남발.  
    - 안정성 문제: 잘못된 매칭으로 ViewHolder 상태(체크박스, 선택상태) 전파 오류/깜빡임.
  - 예시 코드나 상황 예시  
    - 서버가 동일 글을 매 요청마다 새 객체로 보내면, ID가 없을 때 매 프레임 `notifyItemChanged` 범람.

- **장점**
  - (사실상 없음) 임시로 ID 없이도 동작은 가능.

- **단점/주의점**
  - 성능 저하: 계산량↑, 불필요한 rebind/레이아웃 패스.  
  - UX 저하: 스크롤 깜빡임, 애니메이션 튐.  
  - 상태 불일치: ViewHolder 잔상, 선택 상태 엉김.

- **핵심 답변 요약**
  - 상황: ID 없이 DiffUtil 사용  
  - 원인: 항등성 판단 실패  
  - 해결: 안정 ID 제공(서버 PK/로컬 생성 UUID) 또는 `stableIds` 사용

- **면접 대답용**
  > “ID 없으면 `areItemsTheSame`가 흔들려 이동/삽입을 잘못 판단합니다. 불필요한 바인딩과 깜빡임이 늘고 상태 잔상이 생겨요. 그래서 서버 PK나 로컬 UUID로 안정 ID를 보장합니다.”

### [ListAdapter를 사용할 때 DiffUtil이 어떻게 동작하며, 어떤 식으로 변경된 아이템만을 갱신하는지 좀 더 자세히 설명해주실 수 있을까요?]

- **면접 대답용**
  > “`submitList` 때 이전/현재를 비동기로 diff하고, ID로 매칭한 뒤 내용만 달라지면 payload로 해당 뷰만 갱신합니다.”


### [DiffUtil을 직접 구현해보려면 어떤 절차가 필요하며, DiffUtil의 주요 메서드들은 무엇이 있고 각각의 역할은 무엇인지 설명해주실 수 있을까요?]
- **용어 설명**
  - ItemCallback / DiffUtil.Callback.

- **세부 설명**
  - 상황 설명  
    - 커스텀 비교 로직 필요.
  - 구체적인 동작/원리  
    - `DiffUtil.Callback` 구현: `getOldListSize`, `getNewListSize`, `areItemsTheSame`, `areContentsTheSame`, `getChangePayload`.  
    - 또는 `ListAdapter`라면 `ItemCallback` 두 메서드 + payload override.
  - 예시 코드나 상황 예시
    ```kotlin
    data class Post(val id: Long, val title: String, val liked: Boolean)
    object PostDiff : DiffUtil.ItemCallback<Post>() {
        override fun areItemsTheSame(a: Post, b: Post) = a.id == b.id
        override fun areContentsTheSame(a: Post, b: Post) = a == b
        override fun getChangePayload(oldItem: Post, newItem: Post): Any? =
            buildSet {
                if (oldItem.title != newItem.title) add("title")
                if (oldItem.liked != newItem.liked) add("liked")
            }.ifEmpty { null }
    }
    ```

- **장점**
  - 최소 갱신·정확한 애니메이션.

- **단점/주의점**
  - 비교 비용 높은 필드 남용 금지.

- **핵심 답변 요약**
  - `areItemsTheSame`(항등), `areContentsTheSame`(동등), `getChangePayload`(부분 업데이트).

- **면접 대답용**
  > “콜백은 크기 두 개, 비교 두 개, 필요 시 payload까지 구현합니다. ID로 항등성, 내용으로 동등성을 나눠야 합니다.”


### [리사이클러뷰에서 뷰홀더를 사용하는 이유는 무엇인가요?]

    - 한 번 바인딩한 자식 뷰 참조를 홀더에 저장 → 재바인딩 때 즉시 사용.

- **단점/주의점**

- **핵심 답변 요약**
  - 참조 캐싱으로 성능 확보.

- **면접 대답용**
  > “`findViewById`를 매번 하지 않도록 참조를 캐싱합니다. 그래서 스크롤이 부드러워집니다.”

### [뷰홀더에 이너 클래스를 사용할 때 주의사항은 무엇인가요?]
- **용어 설명**
  - Inner class: 외부 클래스 참조를 암묵적으로 보유.

- **세부 설명**
  - 상황 설명  
    - ViewHolder를 어댑터의 inner로 선언.
  - 구체적인 동작/원리  
    - 암묵적 외부 참조로 메모리 누수 위험(RecyclerView/Activity 체인).  
    - 정적 중첩 클래스(`class VH(...) : RecyclerView.ViewHolder` 외부 `inner` 제거) 권장.
  - 예시 코드나 상황 예시  
    - `inner class VH` → 어댑터 생명주기 길어지면 컨텍스트가 해제되지 않음.

- **장점**
  - 외부 멤버 접근이 편함.

- **단점/주의점**
  - 메모리 누수·예상치 못한 참조 유지.

- **핵심 답변 요약**
  - `inner` 지양, 필요하면 `WeakReference`/인터페이스 콜백.

- **면접 대답용**
  > “ViewHolder는 `inner` 대신 정적 클래스로 두고, 콜백만 주입해 외부 참조를 끊습니다.”


### [이너 클래스에서 상위 클래스 프로퍼티를 안전하게 참조하기 위한 방법은 무엇이 있나요? (Hint: WeakReference와 관련된 개념)]
- **용어 설명**
  - WeakReference: GC가 가능하도록 약한 참조.

- **세부 설명**
  - 상황 설명  
    - 이너 클래스가 외부 Activity/Adapter를 오래 붙잡는 문제.
  - 구체적인 동작/원리  
    - 상위 객체를 `WeakReference`로 감싸고, 사용 시 `get()`으로 안전 접근(널 체크).  
    - 콜백 인터페이스로 최소 정보만 의존.
  - 예시 코드나 상황 예시
    ```kotlin
    class SafeListener(owner: Owner) {
        private val ref = WeakReference(owner)
        fun onClick() { ref.get()?.doSomething() }
    }
    ```

- **장점**
  - GC 방해 최소화.

- **단점/주의점**
  - 언제든 null → 방어 코드 필요.

- **핵심 답변 요약**
  - 상위 참조는 약하게, 접근 시 널 가드.

- **면접 대답용**
  > “외부 참조는 `WeakReference`로 약하게 들고, 매 접근마다 널 체크로 안전하게 씁니다.”


### [WeakReference를 사용하여 메모리 누수 문제를 해결할 때 주의할 점은 무엇인가요? (Hint: ReferenceQueue)]
- **용어 설명**
  - ReferenceQueue: 참조 객체가 GC된 시점을 통지받는 큐.

- **세부 설명**
  - 상황 설명  
    - 리스너/작업 큐에 등록된 약한 참조가 GC된 뒤에도 컬렉션에 남아있는 문제.
  - 구체적인 동작/원리  
    - `WeakReference(obj, queue)`로 생성 → 큐를 폴링해 죽은 참조를 정리(compact).  
    - 멀티스레드 환경에서 동기화 필요.
  - 예시 코드나 상황 예시
    ```kotlin
    val q = ReferenceQueue<Owner>()
    val refs = mutableListOf<WeakReference<Owner>>()
    // 주기적으로:
    while (true) { (q.poll() ?: break)?.let { refs.remove(it) } }
    ```

- **장점**
  - 누적된 ‘좀비 참조’ 정리로 메모리 안정.

- **단점/주의점**
  - 큐 폴링 루틴/동기화 비용.

- **핵심 답변 요약**
  - 약한 참조만으로 충분치 않음 → 큐로 정리 루틴 필요.

- **면접 대답용**
  > “`WeakReference`는 대상만 해제될 뿐 리스트엔 남을 수 있어요. `ReferenceQueue`로 해제 시점을 받아 컬렉션에서 제거합니다.”


### [WeakReference와 ReferenceQueue를 함께 사용하는 이유는 무엇인가요?]
- **용어 설명**
  - 약한 참조 + 해제 통지.

- **세부 설명**
  - 상황 설명  
    - 장시간 동작하는 매니저/버스/캐시에서 참조 리스트 청소 필요.
  - 구체적인 동작/원리  
    - `WeakReference`가 대상의 수명에 개입하지 않음 → 대상이 수거되면 큐로 통지 → 자료구조에서 해당 참조 제거.  
    - 메모리 누수/성능 저하 예방.
  - 예시 코드나 상황 예시  
    - 이벤트 버스에 등록된 리스너를 약한 참조로 보관 + 큐로 자동 청소.

- **장점**
  - 자동 청소로 안정성↑, 수동 관리 비용↓.

- **단점/주의점**
  - 구현 복잡성, 스레딩 고려.

- **핵심 답변 요약**
  - 약하게 잡고, GC 시점을 큐로 감지해 자료구조를 동기 정리.

- **면접 대답용**
  > “약한 참조만 두면 리스트엔 껍데기가 남습니다. `ReferenceQueue`로 GC 시점을 받아 컬렉션에서 제거해 메모리와 성능을 함께 지킵니다.”

### [리사이클러뷰에서 페이징을 구현하는 방법에 대해 설명하시오.]
- **용어 설명**
  - 페이징(Paging): 대용량 데이터를 페이지 단위로 나눠 필요할 때마다 점진적으로 로드하는 기법.
  - Paging3: Jetpack 라이브러리로, 네트워크/DB 연동, 캐싱, 로드 상태 관리까지 표준화.

- **세부 설명**
  - 상황 설명  
    - 긴 피드(뉴스, 쇼핑 목록)를 초기 한 번에 다 불러오면 느리고 메모리 낭비. 스크롤에 맞춰 필요한 만큼만 로드해야 함.
  - 구체적인 동작/원리  
    1) `PagingSource<Key, Value>`가 “어떤 키로 다음 페이지를 로드할지” 정의  
    2) `Pager(PagingConfig, pagingSourceFactory)`가 `Flow<PagingData<Value>>` 생성  
    3) UI는 `PagingDataAdapter`에 `submitData(lifecycle, pagingData)`로 전달  
    4) 스크롤 위치에 따라 `LoadType.REFRESH/APPEND/PREPEND`가 자동 호출되어 추가 데이터 요청
  - 예시 코드나 상황 예시
    ```kotlin
    // Repository
    fun posts(): Flow<PagingData<Post>> =
      Pager(
        config = PagingConfig(pageSize = 20, prefetchDistance = 5, enablePlaceholders = false),
        pagingSourceFactory = { PostPagingSource(api) }
      ).flow

    // ViewModel
    val paged = repo.posts().cachedIn(viewModelScope)

    // UI
    lifecycleScope.launch {
      viewModel.paged.collectLatest(adapter::submitData)
    }
    ```

- **장점**
  - 스크롤 연동 자동화, 메모리/네트워크 사용 절감, 로드 상태 표준 처리.

- **단점/주의점**
  - 데이터/키 설계 필요, 다중 소스(캐시+네트워크)는 `RemoteMediator`까지 고려해야 함.

- **핵심 답변 요약**
  - `PagingSource→Pager→Flow<PagingData>→PagingDataAdapter` 파이프라인으로 스크롤에 맞춰 점진 로드.

- **면접 대답용**
  > “`Pager`로 `Flow<PagingData>`를 만들고, `PagingDataAdapter`에 `submitData`만 하면 스크롤에 맞춰 자동으로 `APPEND/REFRESH`가 동작합니다. 페이지 크기/프리패치만 적절히 잡으면 메모리·네트워크 모두 효율적이에요.”


### [안드로이드에서 사용되는 Paging Library의 주요 구성 요소에는 어떤 것들이 있고 각각의 역할은 무엇인가요?]
- **용어 설명**
  - `PagingSource<Key, Value>`: 페이지 로드 로직(네트워크/DB) 정의
  - `LoadParams`, `LoadResult`: 로드 요청/응답 컨테이너
  - `RemoteMediator`: 로컬 DB(캐시)와 원격 소스 동기화 중재자
  - `Pager`, `PagingConfig`: 페이징 파이프라인/설정(페이지 크기, 프리패치 등)
  - `PagingData`: 스트리밍되는 페이지 데이터 컨테이너
  - `PagingDataAdapter`: `DiffUtil` 내장 어댑터
  - `LoadState`: `Loading/NotLoading/Error` 상태

- **세부 설명**
  - 상황 설명  
    - 서버+Room 캐시, 오프라인 지원, 로드 상태/리트라이 필요.
  - 구체적인 동작/원리  
    - 단일 소스면 `PagingSource`; 캐싱 포함이면 `RemoteMediator`가 DB 키 관리/동기화.

- **장점**
  - 표준화·테스트 용이·상태 관리 자동.

- **단점/주의점**
  - 초기 학습 곡선, 키/경계 관리 필요.

- **핵심 답변 요약**
  - 소스는 `PagingSource`, 동기화는 `RemoteMediator`, 파이프라인은 `Pager`, UI는 `PagingDataAdapter`.

- **면접 대답용**
  > “데이터는 `PagingSource`, 캐시 동기화는 `RemoteMediator`, UI는 `PagingDataAdapter`가 맡습니다. `Pager`가 이들을 연결하죠.”


### [PagingSource에서 데이터를 가져오고 처리할 때 Retrofit 또는 Room과 같은 라이브러리를 어떻게 활용할 수 있나요?]
- **용어 설명**
  - Retrofit: 네트워크 클라이언트, Room: 로컬 DB ORM.

- **세부 설명**
  - 상황 설명  
    - 네트워크 전용/DB 전용/하이브리드(캐시+네트워크) 케이스.
  - 구체적인 동작/원리  
    - **네트워크 전용**: `PagingSource.load()`에서 `api.get(pageKey)` 호출 → `LoadResult.Page(data, prevKey, nextKey)`  
    - **Room 전용**: `@Query`가 `PagingSource<Int, Entity>` 반환 → `Pager`에 그대로 전달  
    - **하이브리드**: `RemoteMediator`가 네트워크 가져와 Room에 저장, UI는 Room 기반 `PagingSource`를 구독
  - 예시 코드
    ```kotlin
    // Room: DAO가 PagingSource 제공
    @Query("SELECT * FROM post ORDER BY id DESC")
    fun paging(): PagingSource<Int, PostEntity>
    ```

- **장점**
  - 오프라인·재시작 복원·스크롤 안정.

- **단점/주의점**
  - 키 관리 테이블 필요(하이브리드), 트랜잭션 경계 주의.

- **핵심 답변 요약**
  - Retrofit은 `load()`에서 직접 호출, Room은 `PagingSource`를 바로 제공, 둘 다 쓰면 `RemoteMediator`로 중재.

- **면접 대답용**
  > “Room은 `PagingSource`를 바로 주고, 네트워크는 `load()`에서 호출합니다. 둘을 섞을 땐 `RemoteMediator`로 DB에 넣고 UI는 DB를 구독해요.”

- **면접 대답용**
  > “데이터 클래스는 컴파일러가 `toString()`을 자동으로 만들어 `Class(prop=val)` 형식으로 보여줍니다. 주 생성자 필드만 포함돼요.”

### [클린 아키텍처에서의 레이어 분리에 대해서 설명하세요.]

  - 소규모 프로젝트에는 과도할 수 있음

- **핵심 답변 요약**

- **세부 설명**
  - 상황 설명  
    - DB, API, 캐시 등 다양한 데이터 소스를 통합해 사용해야 하는 경우.
  - 구체적인 동작/원리  
    - 도메인 계층에 인터페이스 제공
    - 구체 구현은 Data 계층에서 담당
    - 데이터 소스 교체 시 도메인 코드 변경 불필요
  - 예시 코드
    ```kotlin
    interface UserRepository {
        suspend fun getUser(id: String): User
    }
    ```

- **장점**
  - 데이터 소스 교체 용이
  - 테스트 시 Mock 주입 가능

- **단점/주의점**
  - 불필요한 추상화는 복잡성 증가

- **핵심 답변 요약**
  - 상황: 여러 데이터 소스 사용
  - 원인: 도메인-데이터 소스 결합 방지
  - 해결 방법: Repository 추상화

- **면접 대답용**
  > "Repository는 데이터 접근을 추상화하여 도메인 로직을 데이터 소스 변경에 독립적으로 유지시킵니다."

    ```kotlin
    interface UserRepository
    ```

  - 결합도 낮춤
  - 모듈 교체 용이

### [코틀린에서 extend와 is 연산자의 차이점은 무엇인가요?]
- **용어 설명**
  - `extends`(정확히는 **상속**): 코틀린은 `:`로 상속/구현을 표현(예: `class A: B(), I`).
  - `is` 연산자: 런타임 **타입 검사**(Java의 `instanceof`와 유사).

- **세부 설명**
  - 상황 설명  
    - 타입 계층을 설계(상속)하는 문제와, 실행 중 객체의 타입을 확인(검사)하는 문제가 다름.
  - 구체적인 동작/원리  
    - 상속: 컴파일 타임 구조(클래스 → 상위 타입).  
    - `is`: 런타임에 객체가 특정 타입/서브타입인지 확인, 참이면 **스마트 캐스트** 가능.
  - 예시 코드나 상황 예시
    ```kotlin
    open class Animal
    class Cat: Animal()

    fun speak(a: Animal) {
      if (a is Cat) a/* 스마트 캐스트 */ // Cat로 간주
    }
    ```

- **장점**
  - 상속: 코드 재사용/다형성.  
  - `is`: 분기 처리 간결화, 안전한 캐스팅.

- **단점/주의점**
  - 상속 남용은 결합도↑.  
  - `is` 과용은 분기 난립 → OOP 원칙 훼손 가능.

- **핵심 답변 요약**
  - 상황: 구조 설계 vs 런타임 검사  
  - 원인: 컴파일 구조(상속)와 실행중 타입 확인(`is`) 목적 차이  
  - 해결 방법: 설계는 상속·구현, 분기는 `is` + 스마트 캐스트

- **면접 대답용**
  > “상속은 타입 계층을 만드는 컴파일 타임 개념이고, `is`는 런타임 타입 검사입니다. `is`가 참이면 스마트 캐스트가 적용돼 안전하게 사용해요.”

  - 무분별한 강제 캐스트는 런타임 예외 초래.

- **면접 대답용**

  - 강제 캐스트 지양, nullable/제네릭 주의.

- **면접 대답용**
  > “플랫폼 타입과 제네릭 소거 때문에 강제 캐스트는 위험합니다.”


### [코틀린에서 스마트 캐스트는 어떤 원리로 동작하며, 어떤 경우에 동작하지 않는지 알고 있나요?]
- **용어 설명**
  - 스마트 캐스트: 컴파일러의 **데이터 흐름 분석** 기반 자동 캐스트.

- **세부 설명**
  - 상황 설명  
    - 타입 검증 후 안전 사용.
  - 구체적인 동작/원리  
    - `is`/널 체크 이후 **해당 변수 재할당이 없고 가시성 보장**이면 캐스트.  
    - 동작 안 함: `var`가 다른 스레드/클로저에서 바뀔 수 있는 경우, 커스텀 getter, 오픈 멤버 등.
  - 예시 코드나 상황 예시
    ```kotlin
    fun f(x: Any?) {
      if (x is String) println(x.length) // OK
    }
    ```

- **장점**
  - 보일러플레이트 감소.

- **단점/주의점**
  - 가변/스레드 안전성 제약.

- **핵심 답변 요약**
  - 불변·재할당 없음이 조건, 아니면 수동 캐스트 필요.

- **면접 대답용**
  > “데이터 흐름 분석으로 안전이 보장될 때만 자동 캐스트됩니다.”


### [코틀린에서 스마트 캐스트의 대표적인 사용 사례는 무엇이며, 어떤 상황에서 유용하게 쓰일 수 있을까요?]
- **용어 설명**
  - 널 안정성, sealed 분기.

- **세부 설명**
  - 상황 설명  
    - 널 체크/타입 분기/패턴 모델링.
  - 구체적인 동작/원리  
    - `if (x != null)` / `when(x)`에서 자동 캐스트.  
    - sealed 클래스의 `when`은 exhaustiveness로 누락 방지.
  - 예시 코드나 상황 예시
    ```kotlin
    sealed interface Result { data class Ok(val v:Int):Result; data object Err:Result }
    fun handle(r: Result) = when(r) {
      is Result.Ok -> r.v // 스마트 캐스트
      Result.Err -> -1
    }
    ```

- **장점**
  - 안전/간결.

- **단점/주의점**
  - 가변성/동시성 제약 동일.

- **핵심 답변 요약**
  - 널/타입 분기에 최적, sealed와 궁합 좋음.

- **면접 대답용**
  > “널 체크나 sealed 분기에서 스마트 캐스트로 코드가 크게 줄어요.”


### [스마트 캐스트를 통해 발생할 수 있는 성능상의 영향에 대해 알고 있나요? 가능하다면 그에 대한 설명을 해주시기 바랍니다.]

- **핵심 답변 요약**
  - 성능 영향은 미미, 다만 빈번 분기는 피하자.

- **면접 대답용**
  > “스마트 캐스트는 컴파일러 기능이라 런타임 오버헤드는 거의 없고, 잦은 타입 분기 자체가 문제입니다.”

### [Kotlin에서 let과 run 함수의 차이점은 무엇인가요?]

    - `let`: **it**을 파라미터로, **람다 결과**를 반환(변환).


- **장점**
  - 널 처리/초기화 간결.

- **단점/주의점**
  - 과용 시 가독성↓.

- **핵심 답변 요약**
  - `let`은 it·변환, `run`은 this·초기화/계산.

- **면접 대답용**
  > “값 변환엔 let, 컨텍스트 내부 초기화/계산엔 run을 씁니다.”

    - `also`: **it** 파라미터, 주로 **부수 효과(로그, 검사)**.
  - 예시 코드나 상황 예시
    ```kotlin
    val view = View(context).apply { id = R.id.x }
      .also { println("created ${it.id}") }
    ```

- **장점**
  - 초기화/체이닝 가독성↑.

- **단점/주의점**
  - 중첩 과용 지양.

- **핵심 답변 요약**
  - apply=설정(this), also=부수 효과(it), 둘 다 원본 반환.

- **면접 대답용**
  > “속성 세팅은 apply, 로깅/체크는 also가 어울립니다.”
